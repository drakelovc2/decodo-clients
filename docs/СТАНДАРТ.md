# СТАНДАРТ РЕГГЕРА — единый шаблон для всех авторегеров

Это канон. Новый реггер делается **копированием этой папки**, а не с нуля.
Примеры «как это работает в бою» — живые реггеры в `autoreg/` (каждый под свой
сервис); шаблон общий и обезличен, конкретика — в самих реггерах.

## 2. Почта (у всех ОДНА — своя)

**apimail, catch-all на нескольких доменах.** Ящик создавать НЕ нужно — адрес
генерится на месте, коды/ссылки читаются админкой. Это единственная почта для
реггеров; сторонние temp-mail (mail.tm и пр.) — легаси, в новые проекты не тащить.

```python
from core.mail import MailClient
mail = MailClient()
addr = mail.new_address()                       # th<random>@<случайный домен>
send = mail.send_address(addr)                  # адрес для ОТПРАВКИ в сервис
code, subj = mail.wait_code(addr, sender_hint="<сервис>")     # 6-значный код
url, subj  = mail.wait_link(addr, sender_hint="<сервис>")     # verify-ссылка
```

### Мультидомен (обязательно)

Все домены идут в ОДИН catch-all движка (`temp-mail` воркер). Адрес берёт
случайный домен из `mail_domains` — это размазывает реги по доменам и спасает
от бана одного домена. На 12.10.2026 рабочих доменов четыре:

```json
"mail_domains":     ["drakebum.pp.ua", "xueta.us.ci", "drakuru.com"],
"mail_dot_domains": ["drakezakuru.com"]
```

- `mail_domains` — домены, проходящие фильтр сервиса напрямую. `new_address()`
  выбирает из них случайный.
- `mail_dot_domains` — домены, которые сервис заблокировал по точному имени.
  Для них `send_address()` добавляет **точку в конце** (`user@dom.com.`) —
  FQDN-форма обходит блок-лист по строке, а почтовый сервер нормализует FQDN и
  письмо падает в тот же catch-all. Работает на jev (`drakezakuru.com`).
- Одиночный `mail_domain` остаётся (совместимость): если `mail_domains` пуст,
  используется он.

Как добавить новый домен — см. `autoreg/farms/jev/ДОМЕНЫ.md` (Email Routing в
Cloudflare + catch-all → воркер `temp-mail`). Воркер принимает ЛЮБОЙ
маршрутизированный домен, править его биндинги не нужно.

Правила (набито практикой):
- `User-Agent: curl/8.5.0` **обязателен** — сервер 403-ит дефолтный UA питона.
- Письма бывают QP/base64 → **декодировать MIME**, не грепать сырец регуляркой.
- HTML-письма экранируют `&` → разворачивать `&amp;` перед поиском ссылки.
- `since_ts` отсекает старые письма (иначе подхватится вчерашний код).
- Токен из ссылки тянуть ТУГИМ регексом `[A-Za-z0-9_-]+`: некоторые сервисы
  (Guerrilla) отдают письмо JSON-экранированным, и широкий регекс захватит
  хвостовой backslash → сервис вернёт «link invalid».

Проверка любого адреса (любого домена — движок один):
```bash
curl -s -A "curl/8.5.0" -H "x-admin-auth: 9ZXQprlYCYM8YUv5Qib3g" \
  "https://apimail.drakezakuru.com/admin/mails?address=<addr>&limit=5&offset=0"
```
`offset=0` обязателен — без него движок отвечает `Invalid offset`.

## 3. Прокси

### Источники (по приоритету)
1. **Bright Data** — **креды НЕ хардкодить в своём `config.json`.** Единый источник —
   `bridges2api/autoreg/proxy/ПРОКСИ.json` (`providers.brightdata`: customer / host / zones).
   `core/config.py` подтягивает зоны оттуда сам при `autoreg.enabled=true`; разлив по
   конфигам делает `bridges2api/autoreg/proxy/apply.py`. Панель: `bridges2api/autoreg/proxy/` → :9916.

   Два типа зон, не путать:
   - `kind: "dc"` → **ротирующая** (свежий IP на запрос, sticky по `-session-<метка>`);
     дешевле и быстрее, годится для скрейпа, массовых GET, обхода WAF и для сервисов
     с простым IP-лимитом. **Часть** сервисов с антифродом по типу сети такие IP режет —
     тогда берут ISP/residential. Это зависит от сервиса, а не от зоны: проверяй (см.
     «Сверка IP капчи и сабмита» ниже), не переноси «по умолчанию».
   - `kind: "isp"` → **статичный жилой IP**; чаще проходит там, где сервис смотрит на
     тип сети — логины, Turnstile, антифрод-цепочки.

   Код: `core/proxy.py::SessionRotator` + `make_rotator()` — по умолчанию ISP приоритетнее
   DC; порядок меняется под сервис (нет сверки IP → ротирующий DC выгоднее).
   **ISP-зоны по сессиям НЕ ротируют** — только datacenter.
   Полный гайд: `bridges2api/autoreg/proxy/ГАЙД-РОТАЦИЯ.md` (формат строки, sticky, пин
   страны, «метка без дефисов», грабли).
2. **Статический файл** `data/proxies.txt` — когда зон нет.
3. Фри-листы (`autoreg/tools/proxyfetch.py --source lists`) — **только для скрейпа**,
   для фарма аккаунтов выжжены.

### Правила
- Один аккаунт = один IP на весь флоу (включая капчу и чтение письма). У сервисов
  со сверкой IP капчи иначе капча не примется; у остальных это просто гигиена фарма.
- Не больше 3–5 аккаунтов на IP (линковка фермы).
- Прокси проверять **параллельно** (`check_all`, ThreadPoolExecutor), не по одному.
- `Rotator`, `IspRotator`, `SessionRotator` потокобезопасны — можно крутить параллельными воркерами.

### Сверка IP капчи и сабмита — ПРОВЕРЯТЬ, не предполагать
**Это наблюдение на tokenharbor (10.10), а не универсальный закон.** Там сервис
сверяет, что IP, с которого сминчен токен Turnstile, совпадает с IP сабмита формы;
при несовпадении отвечает `You're doing that a bit fast` (легко спутать с
рейт-лимитом — ретрай/пауза не помогают). Проверено ТОЛЬКО на tokenharbor; для
нового сервиса это **гипотеза**, которую надо проверить самому, а не переносить
«по умолчанию».

Как проверять (та же таблица, что набита на tokenharbor):

| Минт капчи | Сабмит формы | Ожидаемый ответ |
|---|---|---|
| прокси A | прокси A (тот же IP) | проходит |
| прокси A | прокси B (другой IP) | если сверка есть → ошибка вида «too fast» |

Практика:
- **Если сверка есть — минт и сабмит идут через ОДИН и тот же прокси.** Для этого
  `config.turnstile_mint_direct: false` (минт тем же прокси) либо `IspRotator`
  с липкой сессией (`-session-<id>`), чтобы IP не менялся между минтом и сабмитом.
- **На сервисах со сверкой IP виджет Turnstile может не отрисоваться под частью зон**
  (нет `script[src*=turnstile]`, нет `input[name=cf-turnstile-response]`) — тогда минт
  через эту зону невозможен, а не «медленный». Какие именно зоны не рисуют виджет —
  свойство КОНКРЕТНОГО сервиса; проверка через браузер: открыть страницу через зону и
  посмотреть эти два признака. (Наблюдение с tokenharbor: там не рисовали datacenter и
  часть ISP — это не переносится на другие сервисы автоматически.)
- **Ротирующие ISP-зоны** дают свежий IP на запрос, а с `-session-` — липкий. Годятся
  для сервисов, которые не требуют капчу с «доверенных» IP; для требующих капчу —
  только если виджет через зону рисуется.
- **Два разных лимита не путать:** «too fast» = сверка IP; «Too many sign-ups from
  this network» = per-network кап (лечится только сменой сети/ожиданием).

### 4.1. reCAPTCHA v2 — свой стек ($0), в шаблоне уже есть

`core/recaptcha.py` минтит токен В КОНТЕКСТЕ СТРАНИЦЫ (рендерит виджет в свой
div, жмёт чекбокс, решает сетку, `grecaptcha.getResponse`) — поэтому домен и
TLS совпадают по построению. Сетку решают два солвера:

| `grid_solver` | Что делает | Время |
|---|---|---|
| `classifier` | ONNX YOLO11x-cls, 14 классов reCAPTCHA по тайлу | ~0.2 с |
| `vlm` | OpenAI-совместимая VLM видит монтаж с номерами | ~15 с |
| `auto` (дефолт) | классификатор → VLM, если классификатор ничего не нашёл | 0.2–15 с |
| `both` | объединение ответов | ~15 с |

Конфиг (ключи уже прописаны в `config.example.json`):

```json
"recaptcha_sitekey": "",
"captcha_solver": "auto",            // auto | browser | vlm | 2captcha
"grid_solver": "auto",
"grid_api_base": "https://8090-…instabox.tech",  "grid_api_key": "ibp_…",
"vlm_api_base":  "https://8087-…instabox.tech/v1", "vlm_api_key": "ibp_…",
"vlm_model": "lfm3-recaptcha",
"stt_api_base":  "https://8088-…instabox.tech/v1", "stt_api_key": "ibp_…",
"stt_model": "whisper-small",
"twocaptcha_key": ""
```

Готовый стек без GPU (4 vCPU / 8 ГБ): ONNX-классификатор + LFM3-VL-2B-recaptcha
на llama.cpp + faster-whisper — развёртывание и грабли в
`провайдеры/sandboxes-vm/instabox-vision.md`. Env-переменные `VLM_API_BASE` /
`GRID_API_BASE` / `STT_API_BASE` (и `_KEY` / `_MODEL`) перебивают конфиг.

Две вещи, на которых легко обжечься:

1. **VLM на CPU отвечает 15–20 с.** Любой прокси с таймаутом молчания (~20 с)
   отдаст `502`, поэтому `ask_vlm` ходит **стримом** (`stream: true`).
2. **Классификатор кормить только сырыми payload-тайлами** (300×300), без
   рамок/номеров и без монтажа — на размеченной картинке он путается.
   Монтаж с номерами — для VLM.
3. Классификатор пропускает мелкие объекты (зелёный светофор в углу) — для
   этого и нужен `auto`/`both`, а не чистый `classifier`.

## 5. Баланс и лимиты (модуль `core/limits.py`)

**Главный принцип: лимит считать в ДОЛЛАРАХ по прайсу, не в токенах и не в запросах.**
(Так, например, устроен tokenharbor: «list-price value of the work». Но это свойство
КОНКРЕТНОГО сервиса — у другого лимит может считаться в токенах или запросах;
проверь, в чём измеряется лимит твоего сервиса, и правь под него.)

- Своя тарификация: `usd_for(prices, model, prompt_tokens, completion_tokens)`
  → `токены × цена платного аналога` (у `*:free` роутов `pricing = 0`!).
- Прайс: `GET /v1/models` → `pricing.{input_usd_per_1m, output_usd_per_1m}`, кэш в `data/prices.json`.
- Квоты аккаунта: `GET /api/me/free-tier` (**нужна сессия после login**):
  `req_used`, `used_pct`, `exhausted`, `reset_at`, `model_ids[]`.
- Полный лимит в $ сервер не отдаёт → **измерить**: накрутить известную стоимость,
  снять `used_pct` до/после → `лимит ≈ Δspent / (Δpct/100)`. Вписать в
  `config.json → free_allowance_usd_per_account`.
- Период сброса — **скользящий 7×24ч от первого запроса** (не календарная неделя).
- При исчерпании — rate-limit ошибка (429), баланс не тратится.
- Массовый сбор квот рейт-лимитится (429 на login) → `collect(max_workers=3)` + пауза + бэкофф.
- **Расход считаем САМИ, локально, в реальном времени** — из своего леджера
  (`data/usage.jsonl`), а не опросом сервера. Опрос сервера = логин по каждому аккаунту:
  медленно (минуты на сотни акков) и упирается в 429. Фон-опрос по умолчанию ВЫКЛЮЧЕН
  (`limits_bg_interval_sec: 0`); сервер спрашиваем только кнопкой «Сверить с сервером».
- **Исчерпанные аккаунты скрываются и уводятся из ротации.** Лимит возвращается ровно
  через **7×24ч от ПЕРВОГО free-запроса** (личное скользящее окно). Локально: если наш
  учёт выбрал лимит $ → аккаунт `exhausted`; в панели чекбокс «скрыть исчерпанные»,
  в строке — «сброс YYYY-MM-DD» (оценка = первое использование + 7 дней); в мосте такие
  ключи паркуются статусом `exhausted` и не берутся в ротацию.

## 6. Панель (PANEL-SPEC) — что обязано быть

Обязательные вкладки и блоки:

1. **Шапка**: сервис, статус, счётчики (аккаунтов ok/fail/?), бейдж моста, последний прогон.
2. **Регистрация**: поле `count` (до 500), поле `потоков` (1–12), кнопки
   «▶ Регистрировать» и **«⚡ Параллельно»**, прогресс-бар done/total, **строка на каждый
   воркер** с текущим шагом (k/6), кнопка «Стоп».
3. **Вкладка Аккаунты**: email, статус-бейдж, api_key с копированием, free ✓/✗, создан.
4. **Вкладка Модели**: `/v1/models` + пометка **доступна (free) / только платно**
   (не все «available» реально доступны).
5. **Вкладка Лимиты** (дашборд баланса): «сожжено токенов / ещё можно сжечь / сожжено $ /
   осталось $ / % лимита» + таблица по аккаунтам + **таблица расхода по моделям**
   (запросы, токены, $, $/1M in/out, сколько токенов влезает в лимит).
6. **Вкладка Пул моста**: alive/cooldown/dead, статус refill.
7. **Вкладка Мост**: живой фид апстрим-запросов (статус, скорость, токены, $, ошибки),
   сводка avg/p95/макс и хвост `bridge.log`; авто-обновление 5с. Нужна для диагностики
   («долго отвечает / обрывается» видно сразу).
8. **Вкладка Подключение**: BaseUrl/ApiKey/ModelID + готовые сниппеты (curl, Python, IDE).
9. **Логи**: tail, авто-рефреш 5с.
10. **Живое обновление**: вкладки «Лимиты» и «Мост» авто-рефрешатся каждые 5с —
    расход токенов и запросы видны в реальном времени, без нажатия «Обновить».
11. **Сортировка — везде**: каждый заголовок таблицы кликабелен (↑/↓). Обязательные
    сортируемые поля: Аккаунты — email/статус/free/создан/запросы; Модели —
    id/статус (доступные выше платных); Лимиты — статус/запросы/токены/$/%/сброс;
    Расход по моделям — модель/запросы/токены/$/цены; Мост — время/модель/статус/
    скорость/токены/$. Реализация: `DATA` + `SORT` + `sortRows()` + `setSort()` +
    `renderX()` (перерисовка из кэша, без повторного запроса).

Правила панели:
- Слушает **только 127.0.0.1**, свой порт, stdlib (`http.server.ThreadingHTTPServer`),
  без новых pip-зависимостей; один HTML без CDN, тёмная тема.
- `start.sh` гасит свой порт перед стартом (`fuser -k -n tcp <порт>`), пишет в `data/panel.log`.
- Авто-рефреш summary/job каждые 5с.

## 7. Параллельная регистрация

- `workers` воркеров, каждый берёт **свой прокси** (`rot.next()`) и ведёт аккаунт целиком.
- Общая очередь задач под `Lock`; счётчики (`done/ok/fails`) — тоже под `Lock`.
- `currents[]` в состоянии job — строка прогресса на воркер (панель их рисует).
- **Мягкий circuit breaker**: N фейлов подряд → пауза 60с и продолжай (не стоп);
  жёсткий стоп только при 3N.
- Атомарная запись состояния: **уникальный `.tmp` на поток** + лок на `os.replace`
  (иначе гонка и `FileNotFoundError` — набито).
- Пауза между аккаунтами: 3с с прокси (IP разные), 25с напрямую (один IP).

## 8. Мост (OpenAI-шлюз) — если у сервиса есть API

### 8.00. Язык моста — Python, только stdlib (обязательно)

Все **новые** мосты пишем на Python: `http.server` + `urllib` + `json`,
без зависимостей. Go для этой задачи не даёт выигрыша, а стоит дорого:

- Windows и чужая машина: Go-мост — это собранный `.exe` под каждую
  платформу. Без Go-тулчейна его не собрать и не поправить; Python есть
  там, где есть реггер, и `python3 server.py` одинаково работает на
  Linux, Windows и macOS;
- нет рассинхрона «бинарь старее исходника»: у нас уже было, когда
  собранный мост жил со старыми заголовками, а в коде уже стояли новые;
- правка — это правка одного файла, без пересборки и раздачи бинаря.

Производительности stdlib-сервера (`ThreadingHTTPServer`) хватает с
запасом: узкое место — апстрим, а не проксирование.

**Исключение:** существующий Go-мост `autoreg/Zcode2Api` остаётся как есть
— легаси, переписывать без причины не нужно. Новые мосты — только Python.
Если когда-нибудь упрёмся в пропускную способность, сначала замеряем и
только потом обсуждаем другой язык.

**Мост живёт ОТДЕЛЬНО от папки реггера**: каноническое место — `bridges2api/active/poolgateways/<имя>/`
(папка намеренно не связана с автореггерами). У каждого моста свой `start.sh`
(гасит свой порт, лог в `data/`) и свой `config.json`.

### 8.0. ГИГИЕНА ИМЁН — мост не знает про авторег (обязательно)

Мост — это **самостоятельный шлюз к пулу ключей**, а не «придаток реггера».
В коде, конфиге, README, комментариях, логах и любых строках, видимых клиенту
или на сервере, **НЕ должно быть ни одного упоминания** авторега/реггера:

- запрещены слова: `реггер`, `авторег`, `autoreg`, `регистрация`, `фарм`, `farm`,
  `банк аккаунтов`, `accounts.jsonl реггера`;
- запрещён `project_root`, указывающий в папку реггера; пул пополняется
  **нейтральным** скриптом (`import_keys.py <файл>`) или файлом `data/keys.txt`;
- запрещены относительные пути вида `../../../autoreg/<реггер>/…` — мост не должен
  знать, что реггер вообще существует.

Правильные формулировки: «пул API-ключей», «шлюз к пулу», «загрузить пул ключей».
Всё, что видно с сервера, читается так: **это автономный шлюз, развёрнутый на
амазоновском сервере** (AWS EC2 `raa`, `3.141.146.56`), и больше ничего.

**Почему:** мост может попасть в чужие руки / на общий сервер / в лог; связь
«ключи ← авторег» не должна из него торчать. Читающий код не должен понять, что
ключи откуда-то нафармлены.

### 8.1. Что должен делать мост

- `POST /v1/chat/completions` (+ stream passthrough), `GET /v1/models`, `GET /health`.
- Пул ключей из файла (`data/keys.txt`, hot-reload по mtime), round-robin;
  401/403 → dead, 429 → cooldown, 5xx → следующий ключ.
- **Леджер** `data/usage.jsonl`: `ts, key_prefix, tool/model, status, latency_ms, usd`
  — для локальной статистики запросов.
- **403 различать**: WAF-челлендж (`challenge`/`captcha`/`waf`) НЕ убивает ключ —
  иначе пул выжигается (набито: 44 ключа); убивать только на `invalid_api_key`/`revoked`.
- **Прокси для апстрима** (`upstream_proxy` = `brd`|`file`|`none`): ротация IP
  на запрос убирает WAF-челленджи и «залипания» апстрима.
- Клиенту ключ не нужен — мост подставляет ключ пула сам.
- **Гайд рядом**: `GATEWAY.md` в папке моста — что это, зачем, как поднять,
  как пополнить пул, грабли. Пишется нейтрально (см. §8.0).

### 8.1a. Уборка неактивных ключей — `prune_keys.py` (обязательно)

Мост помечает ключ `dead` только когда на него **уже пришёл** запрос. Ключ с
исчерпанным балансом или отозванный может неделями висеть в пуле и жрать ротацию
(набито на backboard2api: **52 повтора на один ключ** с минусовым балансом).
Поэтому у каждого моста — скрипт `prune_keys.py`, который чистит пул целиком:

```bash
python3 prune_keys.py            # проверить все ключи, мёртвые → в архив
python3 prune_keys.py --dry-run  # только показать
python3 prune_keys.py --keep-cooling   # не трогать 429/сетевые
```

Что делает:

- проверяет **каждый** ключ живым вызовом (не `GET /threads` — он отдаёт 200
  даже при исчерпанном балансе; проверять именно чат);
- мёртвые переносит в `data/keys_archive/keys-dead-YYYYMMDD-HHMMSS.txt`
  (в шапке — причина по каждому), а не удаляет: ключ может «оживиться» после
  пополнения баланса;
- живые оставляет в `data/keys.txt`, чистит `keys_state.json` от записей о
  выбывших ключах;
- **не перезаписывает пул, если живых не осталось** (чтобы не потерять файл).

Признаки «мёртвого» ключа (кроме 401/403): текст `balance is used up` /
`paused LLM chat` / `credit is reserved` (только free-кредит — чат не оплачен),
отрицательный `paid_credit_usd`.

**Настройка под свой апстрим** (в `config.json` моста):

| Ключ | Смысл | Пример |
|---|---|---|
| `prune_key_prefix` | префикс ключей этого пула | `espr_`, `thk_live_` |
| `prune_chat_path` | путь чата для проверки | `/threads/messages`, `/v1/chat/completions` |
| `prune_balance_path` | путь баланса (подсказка) | `/billing/balance` |
| `prune_probe_style` | формат запроса | `backboard` \| `openai` |

**Защита от выжигания чужого пула.** Если ключи не подходят апстриму
(ответ `Invalid API Key format`) или путь чата не тот (`404`/`405`), скрипт
ставит статус `unknown` и **отказывается перезаписывать пул** — иначе одним
запуском можно было бы вычистить весь мост из-за ошибки в конфиге. Набито
13.10.2026: запуск на мосте с другим форматом ключей показал «725 мёртвых»,
хотя ключи живые — просто проверялись не тем апстримом.

Правила: уборку гонять **после каждого залива пула** и по подозрению на бан;
результат писать в `GATEWAY.md` (сколько выбыло и почему).

### 8.2. Деплой моста

Мост разворачивается **на амазоновском сервере** (AWS EC2 `raa`, us-east-2,
`3.141.146.56`, юзер `ubuntu`, ключ `ggavma.pem`). Раскладка на сервере:
`~/<имя>/` (`server.py`, `config.json`, `data/keys.txt`), запуск — `bash start.sh`,
живёт под `setsid nohup` или systemd-юнитом. Публично не слушает — только
`127.0.0.1`; наружу при необходимости — через SSH-туннель.

> **Не путать серверы:** UpCloud (`209.50.57.179`) — там BRD-прокси заблокирован
> (порты `brd.superproxy.io` фильтруются) и лежат легаси-мосты; деплой нового —
> на AWS. Любые упоминания сервера в доке моста — только амазоновский.


### 8b. BRD session-ротация и релей авторизации для браузера (обязательно)

Датацентровые зоны BRD с суффиксом `-session-<id>` дают **новый exit-IP на каждую
сессию** — это не список из N прокси, а ФАБРИКА. В пуле держим «шаблоны» зон (по
одному на зону), а рабочую сессию минтим в момент попытки (`mint_brd`), поэтому IP
капчи и IP HTTP-части совпадают по построению, и линковки фермы по одному IP нет.
В state-файл пишем ключ шаблона (`state_key`), иначе он пухнет на каждый аккаунт.

**Грабли (набито на conol 09.10):** Chromium **игнорирует логин/пароль** в
`--proxy-server` — молча их вырезает. BRD-прокси всегда с авторизацией, поэтому
браузер в них напрямую не сходит (407, капча не проходит). Решение —
`core/proxy_relay.py`: локальный релей без зависимостей поднимает `127.0.0.1:<port>`,
добавляет `Proxy-Authorization` и туннелирует в апстрим-прокси. Каждой сессии — свой
порт, поэтому смена аккаунта меняет `--proxy-server` и браузер перезапускается.
HTTP-часть (`requests`) релей не нуждается — авторизацию поддерживает сама.

Приоритет источников прокси: явный `cfg`/`path` от вызывающего → env-оверрайд →
BRD-зоны → статический список.

### 8a. Логи — ДВА уровня (обязательно у каждого реггера и моста)

Модуль общий: `core/logging.py` (`make_logger`), конфиг `verbose_log`,
`debug_body_chars`. Обычный лог — короткие строки в `data/<имя>.log` (через
`start.sh`); подробный — JSONL в `data/debug.log` (у моста — `data/bridge_debug.log`).

- **Обычный (`LOG.info`)** — «что случилось», читается глазами, НЕ разрастается:
  `аккаунт 12/500`, `chat [model] → 200 (3.6с)`, `refill: реггер запущен`.
- **Подробный (`LOG.debug(kind, **fields)`)** — всё, что нужно разобрать инцидент
  без воспроизведения:
  - мост: `request_in` (полный payload: system/messages/параметры), `plan`,
    `attempt` (попытка, ключ, линия, прокси, статус, латентность, был ли ротIP),
    `response` / `response_stream` (полное тело; для стрима — собранный текст,
    **reasoning/thinking**, usage, finish_reason), `attempt_error`, `give_up`;
  - реггер: каждый шаг флоу с телом запроса/ответа, коды, ошибки, ретраи.
- Сборка стрима — `sniff_sse(buf, acc)` (в `core/logging.py`): копит
  `content`/`reasoning`/`usage`/`finish`, терпима к мусору и обрезке чанков.
- Выключить: `verbose_log: false` в конфиге или env `*_VERBOSE=0` — тогда
  `LOG.debug` — no-op, подробный файл не пишется.
- `LOG.new_req_id()` — короткий id запроса (`r1-a3f2`) связывает все строки
  одного запроса в подробном логе.

## 9. Общие правила (не нарушать)

1. **Запуск python на этой машине** — только:
   `env -u PYTHONHOME -u PYTHONPATH -u LD_LIBRARY_PATH python3 …`
2. **Результат писать сразу после каждого аккаунта** (атомарно), чтобы падение на 90-м
   не теряло 89.
3. **Проверка живости — отдельный шаг** (login / баланс / get-session), не «200 = успех».
4. **Ретраи**: капча-фейл → свежий токен; «email занят» → новый адрес (не ретрай);
   429 → backoff, не долбить.
5. **Circuit breaker** — обязателен (мягкий для длинных прогонов).
6. Секреты — только в `config.json`/env, в git не кладём.
7. Серверы после тестов **гасить**, только свои (`fuser -k -n tcp <свой порт>`).
8. **Шаблон — не догма: чинить его, а не копипастить кривым.** Если под сервис пришлось
   переписать шаблонный модуль (другая капча, другой протокол, другая почта) ИЛИ видно,
   что шаблон можно сделать лучше/универсальнее — это НЕ повод молча разойтись с шаблоном.
   Обязательно: (а) описать в `КОНТЕКСТ.md` своего реггера, что именно не подошло и как
   лучше; (б) внести правку в `_ШАБЛОН-РЕГГЕРА/` — общий код правится в шаблоне, специфика
   остаётся в реггере. Шаблон развивается от реальных реггеров, а не наоборот.
9. **ОТЧЁТ О РАБОТЕ — ОБЯЗАТЕЛЕН (каждая модель, каждый прогон).** Любая модель,
   работавшая в папке проекта (реггер, мост, панель, разовая задача), **обязана
   оставить MD-файл** с отчётом о том, что она сделала. Без отчёта работа не считается
   сделанной. Подробно — §9b.

## 9b. ОТЧЁТ О РАБОТЕ (MD-файл) — обязателен для каждой модели

**Правило:** любая модель (агент), работавшая в папке проекта, **обязана** оставить
после себя **MD-файл с отчётом** о своей работе. Работа без отчёта считается
незавершённой. Это касается реггеров, мостов, панелей и разовых задач.

### Где лежит отчёт

Рядом с местом работы, в подпапке `docs/`:

- **реггер:** `autoreg/<реггер>/docs/ОТЧЁТ-<модель>-<ГГГГ-ММ-ДД>.md`
- **мост:** `active/poolgateways/<мост>/docs/ОТЧЁТ-<модель>-<ГГГГ-ММ-ДД>.md`
  (если подпапки `docs/` нет — создаётся)
- **разовая задача в чужой папке:** `docs/` рядом с изменённым кодом.

Имя модели — как она себя называет (напр. `deepseek-v4.1-flash`, `glm-5.3`).
Дата — день работы. Несколько моделей в один день → отдельный файл на каждую.

### Что обязано быть в отчёте

1. **Кто и когда** — модель, дата, папка/проект.
2. **Что просили** — задача своими словами (одна-две строки).
3. **Что сделано** — конкретно: какие файлы созданы/изменены, какие команды
   запускались, что проверено вживую (с результатом: «аккаунт X, ключ Y, ответ Z»).
4. **Что НЕ получилось / открытые вопросы** — честно, без приукрашивания.
5. **Грабли** — что набито по ходу (чтобы следующая модель не повторяла).
6. **Что дальше** — если осталась незакрытая работа.

### Зачем

- Следующая модель/сессия **входит в контекст по отчёту**, а не по догадкам.
- Видно, **кто что менял** — при поломке ищется автор и причина.
- Работа не теряется: даже если сессия оборвалась, отчёт остаётся на диске.

### Мини-шаблон отчёта

```markdown
# Отчёт: <модель> — <дата>

**Проект:** <папка>
**Задача:** <что просили>

## Сделано
- <файл>: <что именно>
- проверено вживую: <команда> → <результат>

## Не получилось / открыто
- <пункт>

## Грабли
- <пункт>

## Дальше
- <пункт>
```

## 9a. Структура и гигиена папки (чтобы не было мусора)

**Каждый реггер и каждый мост ОБЯЗАН иметь `start.sh`** — без аргументов, гасит свой
порт перед стартом, пишет лог в `data/`. Мост — свой `start.sh` в своей подпапке.

### Что где лежит (и что НЕ лежит в корне)
```
<реггер>/
  start.sh                 ← ОБЯЗАТЕЛЬНО (единственный запускатор панели)
  main.py                  ← CLI
  config.json / config.example.json
  core/                    ← вся логика (модули, не скрипты)
  panel/                   ← server.py + static/index.html
  data/                    ← ВСЁ изменяемое: аккаунты, логи, state, прокси, кэши
  docs/                    ← README.md, PROTOCOL.md, CAPTCHA.md
  tests/selfcheck.py
  КОНТЕКСТ.md
  .gitignore               ← config.json, data/, __pycache__/
```

### Правила гигиены (в корне — только точки входа и метаданные)
1. **Корень = вход + конфиг + доки.** Любой рабочий файл — в `core/`, любой вывод — в `data/`.
2. **Никаких `*.bak-*`, `*.tmp`, `__pycache__`, `*.log`, скриншотов и видео в корне.**
   Бэкапы — в `bak/` или `data/bak/`; логи — только `data/`.
3. **`data/` в `.gitignore`** целиком (там аккаунты и ключи).
4. **Одна папка = один реггер.** Общий код — не копипастой, а через `_ШАБЛОН-РЕГГЕРА/`.
5. **Мосты НЕ внутри реггера** — `bridges2api/active/poolgateways/<имя>/` (переносятся
   из временного `poolgateways/`; свой `start.sh`, `config.json` с `project_root`).
6. **Порт не занять, пока не вписан в реестр.** Любой новый порт (панель, мост,
   вспомогательный сервис) ОБЯЗАН быть в `PORTS.md` **ДО первого запуска**, с полями:
   порт · что слушает · где зашито (`файл:строка`) · статус (живой/резерв). Панели реггеров
   дополнительно — в `autoreg/docs/PANEL-PORTS.md`. Свободность проверять
   `ss -tlnH 'sport eq :<порт>'` (пусто = свободен). Меняешь порт — правишь **реестр +
   конфиг + `start.sh`** в один заход.
7. **Один вход на действие**: запуск панели — только `start.sh`, не «python panel/server.py»
   в доке (иначе разъезжается с портом/логами).
8. **Имя модуля = его роль**: `mail.py`, `proxy.py`, `limits.py`, `results.py` — одинаково
   во всех реггерах (чтобы код переносился без правок).

### Проверка структуры (перед сдачей)
```bash
cd autoreg/<реггер>
ls                          # в корне: start.sh main.py config*.json core/ panel/ data/ docs/ tests/ *.md .gitignore
ls data/                    # всё изменяемое здесь
grep -rL "start.sh" README.md 2>/dev/null   # доки ссылаются на start.sh, не на python напрямую
find . -maxdepth 1 -name "*.bak-*" -o -name "*.log" -o -name "*.tmp"   # пусто
```

## 11. Общий пульт: реггер подключается САМ

Все мосты и реггеры видны в одной панели — `bridges2api/control` (http://127.0.0.1:9917,
вкладки Сервисы / Модели / Авторег / Прокси / Порты). **Вписывать реггер в чужой
реестр не нужно.**

### 11.1. Самоописание `control-service.json`

Положи рядом с реггером файл `control-service.json` — пульт найдёт его сам
(сканирует `active/*`, `active/poolgateways/*`, `autoreg/*`) и подмешает к реестру.
В шаблоне он уже лежит: скопировал папку — поправил `id`, `name`, `port`.

```json
{
  "id": "my-register",
  "name": "my-register",
  "group": "Авторег",
  "kind": "autoreg",
  "start": "bash start.sh",
  "port": 9918,
  "panel": "http://127.0.0.1:9918",
  "proxy": "recommended",
  "note": "панель реггера"
}
```

`cwd` вычисляется по месту файла — писать не надо. Папки, начинающиеся с `_`
(шаблон, архив), пульт пропускает. Если тот же `id` уже есть в
`control/services.json`, побеждает запись оттуда (её можно использовать как
переопределение).

### 11.2. Политика прокси: `proxy`

Отвечает на вопрос «нужен ли сервису прокси». Три значения:

| `proxy` | Смысл | Что делает пульт |
|---|---|---|
| `required` | **без прокси не работает вообще** | кнопка «старт» заблокирована, пока прокси выключен; попытка старта отклоняется |
| `recommended` | обычно ходит через прокси, но может и напрямую | стартует всегда, но показывает жёлтый бейдж «желат. · выкл» |
| `optional` | прокси не важен | ничего не показывает |

Для реггеров ставь `recommended` (им прокси нужен для антифрода — 1 аккаунт = 1 IP).
`required` — только если сервис без прокси не живёт вовсе: так помечен, например,
`freebuff` (он гео-привязан и без US-прокси не поднимается).

Прокси берётся из единого источника `bridges2api/autoreg/proxy/` (§3), у реггеров
это тумблер `autoreg.enabled`, у мостов — `master.enabled`.

### 11.3. Откуда пульт берёт модели

Вкладка «Модели» тянет `/v1/models` у живого моста. Чтобы список был виден и когда
мост лежит, можно указать статический каталог: `models_file` + `models_key`
(точечный путь до списка) + `models_field`. Живой запрос всегда приоритетнее файла.

### 11.4. Модели и цены — сервис описывает САМ

Цену и доступность моделей знает только владелец сервиса, поэтому реггер/мост
обязан написать их **у себя в README.md** — блоком с маркерами:

```markdown
<!-- models:start -->
| Модель | Тариф | Цена | Доступна |
|---|---|---|---|
| deepseek-v4.1-flash | бесплатно | 0 | да |
| gpt-5.5 | платно | $2.5 / 1M | да |
| kimi-k3 | платно | — | нет |
<!-- models:end -->
```

Как это работает:
- пульт (`bridges2api/control`, вкладка «Модели») находит блок по маркерам и
  подмешивает цену/доступность к живому списку из `/v1/models`;
- модели, объявленные в README, но не отдаваемые мостом, показываются с пометкой
  «объявлена» — полезно, когда доступ к модели закрыт;
- если мост сам сообщает тариф (поле `free` в ответе `/v1/models`) — его слово
  авторитетнее, README уточняет цену;
- маркеры внутри ```-фенсов игнорируются, так что пример в документации не
  попадёт в данные.

Правила: порядок колонок свободный (ищем по словам заголовка), обязательны
`Модель` и `Тариф`; тариф — `бесплатно`/`платно` (синонимы free, промо, плат…);
`Доступна` — `да`/`нет`. Файл можно вынести в `models.md` и указать
`"models_doc": "models.md"` в дескрипторе сервиса.

## 12. Разведка, движки, vision, two-phase

Четыре инструмента в шаблоне. Не обязательны для каждого реггера, но снимают
самые дорогие по времени участки работы.

### 12.1. `tools/recon.py` — разведка вместо угадывания

```bash
python3 tools/recon.py https://service.example/signup
python3 tools/recon.py URL --engine camoufox --headed --wait 8
python3 tools/recon.py URL --proxy http://user:pass@host:port
```

Пишет в `data/recon/<host>-<ts>/`:

| файл | зачем |
|---|---|
| `report.md` | человекочитаемо: формы, поля, защита, эндпоинты |
| `summary.json` | то же машинно |
| `skeleton.yaml` | заготовка шагов флоу |
| `requests.jsonl` | сетевые запросы с методами и статусами |
| `page.png`, `page.html` | снимок состояния |

Правила:
- **Селекторы брать из отчёта.** Придуманный селектор — самая частая причина
  «форма не заполнилась».
- `skeleton.yaml` — черновик, а не готовый флоу. OTP-поля, скрытые input'ы и
  капчу проверять глазами.
- SPA без `<form>`: смотреть `loose_fields` и `endpoints`, а не «форм нет».

### 12.2. `core/engines.py` — выбор движка и постоянная личность

```python
from core import engines

eng = engines.resolve("auto", stealth=True)     # camoufox → patchright → playwright
prof = engines.make_profile("data/profiles", account=email, engine=eng)
with engines.launch(eng, prof, proxy=proxy, headless=True) as br:
    page = br.new_page()
```

| движок | когда |
|---|---|
| `camoufox` | Turnstile, Cloudflare, чувствительный отпечаток. Gecko + подмена |
| `patchright` | обычная JS-форма, нужен Chromium-профиль |
| `playwright` | сток, последний вариант, самый детектируемый |
| `invisible` | нужен C++-уровень подмены (ставится отдельно) |

Важно про отпечаток: **camoufox по умолчанию генерирует новый fingerprint на
каждый запуск**. Шаблон это исправляет — первый запуск выбирает реальный
preset устройства, сохраняет в `profile.json`, дальше поднимается с ним же.
Без этого «один аккаунт = одна личность» не выполняется (проверено selftest'ом:
UA, платформа и WebGL менялись между запусками одного профиля).

Проверка личности:

```python
ok, diffs = engines.fingerprint_check(page, prof)
# ok=False → под тем же профилем другой отпечаток, партию гонять рано
```

Правило: **один аккаунт = один профиль**, между аккаунтами и сервисами
профили не переиспользуем.

### 12.3. `core/vision.py` — капча-сетка и аудио

```python
from core import vision
cells, conf = vision.solve_grid_captcha(page, "Select all traffic lights", cells=9)
text = vision.solve_audio_captcha(page)   # скачает mp3 и распознает
```

Нужны `config.vlm_api_base/vlm_api_key/vlm_model` (сетка) и
`stt_api_base/stt_api_key` (аудио). Не настроено → шаг честно падает, а не
отправляет пустое поле. Сетка: модель возвращает индексы, кликает реггер —
координаты зависят от вёрстки, их нельзя зашивать в модуль.

### 12.4. Two-phase: регистрация отдельно, подтверждение отдельно

Когда письмо приходит через 20–60 минут или почта упёрлась в лимит:

```python
client = MailClient()
baseline = client.baseline(address)          # «до» регистрации
# ... форма отправлена, аккаунт ещё не подтверждён
results.save_pending({**account, "mail_baseline": baseline})

# позже, отдельным запуском:
for rec in results.load_pending():
    val, kind = client.wait(address=rec["email"],
                            baseline=rec["mail_baseline"], kind="code")
    if val:
        results.resolve_pending(rec["email"], {"api_key": key})
```

`baseline` обязателен: без него `verify` подхватит старое письмо от
предыдущей попытки. Внутри — `min_id` для apimail и `min_uid` для IMAP.

### 12.5. `tests/selftest_browser.py` + `tools/mock_site.py`

```bash
python3 tools/mock_site.py --port 8765      # локальная цель, сеть не нужна
python3 tests/selftest_browser.py --engine playwright
python3 tests/selftest_browser.py --engine camoufox
```

10 проверок: страница открылась, форма отправлена, письмо получено, код
извлечён, аккаунт подтверждён, verify-селектор найден, сервер подтверждает,
отпечаток сохранён, отпечаток стабилен между запусками, второй профиль
снимает свой. Exit 0 = pass.

Гонять после любой правки `core/engines.py`, `core/mail.py`,
`core/results.py`, `core/vision.py`. Это дешёвая регрессия: 30–60 секунд
против часа отладки на живом сервисе.

### 12.6. Правила, которые чаще всего спасают

- **Один аккаунт — один постоянный профиль.** Не переиспользовать между
  аккаунтами и сервисами.
- **Селекторы — из recon, не из памяти.** При нескольких формах скоупить:
  `#form-id input[name=email]`.
- **`wait_for` вместо `sleep`.** `sleep` — только для осознанного темпа.
- **POST регистрации не ретраить** (`retries: 0`), если сервис не идемпотентен:
  повтор создаёт второй аккаунт или съедает лимит.
- **Секреты не в коде флоу.** Пароли/ключи — в `config.json` (не в git) или
  env, в отчётах и логах маскировать.
- **Не поднимать параллельность, чтобы «продавить» флейк.** Сначала причина.
- **Не фейковать успешный шаг** (телефон, капча, оплата). Пропущенный шаг
  даёт аккаунт, который умрёт на первом же использовании.
- **Падение разбирать по артефактам:** URL, номер шага, ошибка, профиль,
  прокси, скриншот и HTML. Без этого правка — гадание.
